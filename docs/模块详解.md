# MyReview 模块功能详解

> 给后续维护用。业务流程看 `业务流程图.md`，这里讲「每个模块干什么、数据怎么存、往哪儿扩」。

---

## 1. 总体结构

```
浏览器
  └── static/（纯 HTML/CSS/JS，无构建）
        ↓ fetch('/api/...')
  Spring Boot（com.review.vt）
  ├── web/       REST 控制器 + DTO        ← 协议层
  ├── service/   业务逻辑                 ← 核心
  ├── domain/    实体                     ← 与表列 1:1
  └── repo/      存储接口
        └── json/ 本地 JSON 实现（一表一文件）
```

分层只有一条规矩：**web 只做参数校验和 DTO 转换，业务规则一律在 service，存取一律走 repo 接口**。
换存储实现时 service 一行不动。

## 2. domain（实体，与表列 1:1）

| 实体 | 一句话 | 关键字段 |
|---|---|---|
| `Stage` | 分组名字，没有业务含义 | `name`、`summaryJson`（AI 阶段总结） |
| `Practice` | 一个练习 = 一个会话，可反复出卷 | `topic`、`scopeMode`/`scopeText`、`review`、`memoryJson`、`digestJson` |
| `Paper` | AI 一次出的一批题，满分 100 | `status`、`planJson`、`progressJson`、`maxScore`、`summaryJson` |
| `Question` | 一道题 | `tier`、`questionType`、`points`、`referenceAnswer`、`knowledgePointsJson`、`revealedAt` |
| `Attempt` | 一次作答（追加保存） | `answer`、`score`(0-10)、`points`(实得分)、`feedback`、`dimensionsJson` |
| `Source` | 网页抓取缓存 | `url`（即 id）、`title`、`text`、`error` |
| `Note` | 练习笔记条目（per-practice） | `practiceId`、`questionId`(可空)、`scene`(answering/grading/manual)、`text` |
| `Mistake` | 错题本条目（per-practice，一题一条） | `questionId`、`source`(auto/manual)、`reason`、`status`(open/resolved)、`score` |

**分数口径**（只有 `Scoring` 一处，别在别处算）：
- `Question.points` 本题分值，卷内合计 **100**
- `Attempt.score` AI 给的 0-10 表现分
- `Attempt.points` 实得分 = `score/10 × Question.points`
- `Paper.score` = Σ`Attempt.points`（只在 `graded` 时有值）

**错题判定口径**（只有 `MistakeService.isMistake` 一处）：表现分 < `KnowledgeService.PASS_SCORE`(6.0) / 未作答 / 看过参考答案。
手动收录优先——自动收录永不覆盖或删除已有行。

## 3. repo（存储接口）

```
StageRepository / PracticeRepository / PaperRepository
QuestionRepository / AttemptRepository / SourceRepository
NoteRepository / MistakeRepository
```

实现：`repo/json/Json*Repository`，一表一文件（`data/store/*.json`，JSON 数组，行字段 = 表列）。
基类 `AbstractJsonStore`：启动全量进内存、每次变更整体 flush（临时文件 + 原子移动）、
按 id upsert、解析失败备份坏文件后以空库启动、**忽略未知字段**（字段增删旧数据仍可读）。

### 后续换数据库（XML + MyBatis）

约定已经留好，换库时**只加实现、不动业务**：

```
repo/mybatis/MyBatisStageRepository implements StageRepository   ← 新增
repo/mybatis/mapper/StageMapper.java                              ← 接口
repo/mybatis/mapper/StageMapper.xml                               ← SQL 映射
```

要点：
1. **接口方法名照抄**（`findById` / `save` / `findByXxxOrderByYyyAsc`），MyBatis 的 mapper 方法名对齐即可
2. 实体字段名 = 表列名，不用额外的 `@Results` 映射
3. `save` 做成 upsert（`ON CONFLICT(id) DO UPDATE`），与 JSON 实现语义一致
4. `AbstractJsonStore` 的「忽略未知字段」对应 MyBatis 的宽松映射（`map-underscore-to-camel-case` + 不校验列数）
5. 事务：JSON 版本没有事务，MyBatis 版在**级联删除**（`StageService.delete`）上加 `@Transactional` 即可，其余单行操作天然原子

pom 里届时加 `mybatis-spring-boot-starter` + 驱动，再把 `repo/json` 换成 `repo/mybatis` 的 Bean 扫描即可。

## 4. service（核心业务）

| 类 | 职责 | 要点 |
|---|---|---|
| `PracticeService` | 建练习 / 出卷 / 作答 / 交卷 / 看答案 | 业务主干，后台任务都在这 |
| `StageService` | 阶段 CRUD、实时统计、发起全复习 | 不做业务规则，只编排 |
| `StageSummaryService` | **阶段总结（AI 反馈）** | 固定格式喂数据；产出 `reviewScope` |
| `PromptTemplates` | 全部提示词 | 改提示词只动这里 |
| `Scoring` | 分值计算 | 按档位夹在区间内、合计恒 100 |
| `LlmService` | 调模型，返回 JSON | 支持 anthropic / openai 两种协议 |
| `WebFetcher` | 抓网页正文 | jsoup 抽正文，去脚本/导航/页脚 |
| `WebSearch` | 联网搜面经线索 | 校准出题时效性，失败降级 |
| `ReferenceService` | 把范围里的 URL 变成参考资料 | 缓存去重，失败如实报错 |
| `SpeechTranscriber` | 语音转文字接口 | 实现可换（sherpa-onnx / Vosk / whisper.cpp） |
| `SherpaOnnxTranscriber` | sherpa-onnx + Paraformer 实现 | 懒加载、串行 decode、优雅降级 |
| `WavCodec` | WAV → float 采样 | 纯 Java，可单测 |
| `MemoryRules` | 记忆容量与合并 | 并集累积、条数/字数上限 |
| `PromptBudget` | 上下文硬预算 | 防 prompt 膨胀 |
| `Limits` | 容量上限常量 | 见下节 |
| `Mappings` | 实体 → DTO、统计计算 | 百分制统计 |
| `SettingsService` | LLM 配置 | 存 `data/settings.json` |

### 后台任务模型

出题和交卷都是**异步任务**：

```
HTTP 请求 ──> 建记录(status=generating/grading) ──> 立即返回
                     │
                     └── executor.submit(doGenerate / doGrade)
                              │ 每批成功立刻落库 + 更新 progressJson
                              └── 失败记入 failed/error，可 /resume 断点续跑
```

- 线程池 6 线程（出题/批改按批并发）
- `running: Set<paperId>` 保证同一张卷同时只有一个任务；`resume` 时若已在跑会明确报错而不是假装成功
- `progressJson.running` 让前端分得清「还在跑」和「已经停了要点续跑」
- `planJson` 落库 → 重跑时按原计划补缺，不会重复出题

**模型思考（thinking）与输出额度**

`mimo-v2.6-pro` 这类模型默认会先「思考」，而**思考 token 计入 max_tokens**。
上下文一大就思考很久，额度被吃光，正文一个字都剩不下——表现就是
`AI 返回内容为空`，用户只能反复点续跑。

`LlmService.chatJson(system, user, maxTokens, thinking)` 的 `thinking` 开关：

| 调用 | thinking | 为什么 |
|---|---|---|
| 出卷计划 / 分批出题 | **关** | 输出最长，截断风险最高；只要结果不要推理 |
| 本卷总结 / 记忆 / 摘要 / 阶段总结 | **关** | 输出固定格式，不需要推理 |
| 批改 | 开 | 要判断对错与缺失，推理有价值 |

兜底：正文为空且 `stop_reason=max_tokens` 时，自动翻倍额度重试一次。

**交卷的容错分界（重要）**

```
批改（必须成功） →  总结/记忆/摘要/阶段总结（各自容错，失败只降级） → 翻 graded
```

- 批改失败 → 卷停在 grading，可续跑（已批的不重批）
- **总结阶段任一失败都不能把卷卡住**——否则「批阅完却提示任务停止」，用户得反复点续跑
  （这是踩过的坑）。失败时 `paper.summary.failed=true`，前端给出「重新生成总结」按钮
- 卷的 graded 状态翻转在最后，且不依赖总结是否成功

## 语音转文字

**技术选型**：sherpa-onnx + Paraformer（`paraformer-zh-2024-03-09`，普通话+英语）。
选它是因为中文准确率在开源方案里最好，且有 Java 绑定，可以留在单 JVM 里，不用再起 Python 侧车。

### 依赖与平台

sherpa-onnx 的 Java 包走 **JitPack**（不在 Maven Central），pom 里已配好：

```xml
com.github.k2-fsa.sherpa-onnx:sherpa-onnx-jvm:v1.13.5              <!-- JVM API -->
com.github.k2-fsa.sherpa-onnx:sherpa-onnx-native-lib-win-x64:v1.13.5  <!-- native，由 profile 按 OS 注入 -->
```

native jar 里带 `sherpa-onnx-jni.dll` + `onnxruntime.dll`，`LibraryLoader` 自己加载。
换平台只影响 pom 的 profile，代码不动。

### 数据流

```
浏览器 getUserMedia
  → AudioWorklet 采集 PCM（退回 ScriptProcessor）
  → 降采样到 16kHz 单声道
  → 编码 WAV（44 字节头 + PCM16）
  → POST /api/transcribe
  → WavCodec.read() 解成 float[]
  → OfflineRecognizer.decode()
  → {text} 追加进作答框
```

### 三个刻意的设计

1. **懒加载**——native 库与模型只在第一次转写时才初始化，缺模型不影响应用启动；
2. **串行 decode**——sherpa 的 recognizer 不保证并发安全，`transcribe()` 整体加锁；
3. **优雅降级**——任何一步失败都只影响语音功能，`/api/speech/status` 会告诉用户缺什么。

### ⚠️ 两个踩过的坑

**1 · paraformer 只支持 `greedy_search`**

传 `modified_beam_search` 会让 native 层**直接 abort 整个进程**（不是抛 Java 异常，
catch 不住，进程直接没了）。所以 `DECODING_METHOD` 在 `SherpaOnnxTranscriber` 里写死成
`greedy_search`，**不要改成可配**。副作用是热词偏置（`hotwords_file`）对 paraformer 无效
——它只在 `modified_beam_search` 下生效。

**2 · 术语识别差要靠后处理**

中文模型的英文词表有限，equals/volatile 这类术语极易被认成同音词（equals → ecos、
volatile → "瓦太奥"）。热词用不上，改在识别后调一次 LLM 做**术语纠正**
（`POST /api/transcribe/polish`）：只改术语、不改口述内容。

前端是**异步**做的：先把原文填进作答框让用户立刻看到字，再后台纠正、原地替换。
用户已经动手改过就不覆盖。

⚠️ 纠正提示词里**不要举"ecos"这类具体误识例子**——实测模型会把提示词原文连同例子一起吐回来。
同时后端要兜底：结果里出现提示词标记或长度暴涨时，退回原文。

### 上传限制

3 分钟 16kHz 单声道 PCM16 约 5.8MB。Spring 默认的 multipart 限制是 **1MB**，
长录音会被挡在门外（表现是「超出一定长度就无法识别」）。`application.yml` 里已调到 20MB。

**注意**：`paraformer-zh-int8-2025-10-07` 是四川话模型，普通话要用 `paraformer-zh-2024-03-09`。

错误统一 `{"error":"消息"}` + 4xx/5xx（AI 失败 502），见 `GlobalExceptionHandler`。

## 6. 容量限制

| 限制 | 默认 | 在哪改 | 超了会怎样 |
|---|---|---|---|
| 一个阶段最多练习数 | **50** | `Limits.MAX_PRACTICES_PER_STAGE` | 建练习被拒，提示新建阶段 |
| 一个练习最多卷数 | **20** | `Limits.MAX_PAPERS_PER_PRACTICE` | 出卷被拒，提示新建练习 |

按每天 2 卷算，20 卷 ≈ 3 周；50 个练习足够把技术栈切得很细。**日常使用碰不到**，
只是防止有人一口气练几百卷时统计、上下文、文件体积一起变慢。

其他隐式上限（防上下文膨胀，见 `PromptBudget` / `MemoryRules`）：
记忆每类 ≤8 条、每条 ≤30 字，coverage ≤40 条；摘要 ≤400 字；出题上下文总量 ≤12000 字。

## 7. 答题与计分规则（容易记错，写在这）

1. 保存作答**不调 AI**，追加一条 `Attempt`，历史不覆盖
2. **点「看参考答案」要弹确认框**，确认后 `Question.revealedAt` 落库
3. **看过参考答案的题，交卷时直接 0 分**，不交给 AI 批改（前后端口径一致）
4. 交卷只批改「未看答案 且 有作答」的题；未作答的题不得分
5. 卷得分 = Σ各题实得分，满分 100
6. **练习没有「结束」**，一直都在；阶段也没有。想收尾就新建一个
7. **批改标准 = 「本题要求」（`Question.demandsJson`）**，不是参考答案全文：
   - 参考答案只是「要求内正确答案」的样本，它比作答多写的部分**不算缺失、不扣分**，
     只能写进 feedback 的「扩展：」段（不加分不扣分）
   - 但**要求内**答错、概念混淆、问「为什么」只给结论、漏要求项，照常重扣（有分数锚点 10/8/6/4/2/0）
   - 旧题没有 demands → 以题干实际问的内容为准（`Mappings.demandsText` 会给批改 AI 说明这一点）
8. **错题本自动收录**（`MistakeService.isMistake`）：表现分 < 6 / 未作答 / 看过参考答案 → 收进本练习的错题本。
   一题一条（幂等，批改重入不翻倍）；手动收录的行永不被自动覆盖。
9. **练习笔记**：答题时（含看完参考答案后）、看批改点评时、笔记面板手动，三处快记；
   结构化条目（场景 + 题目上下文 + 文字），笔记面板可统一增删改。

## 8. LLM 协议扩展

`LlmService` 里协议差异收敛在三处：`post()` / `buildBody()` / `extractText()`。

现在支持：

| apiFormat | 端点 | 认证 | 谁在用 |
|---|---|---|---|
| `anthropic`（默认） | `{base}/v1/messages` | `x-api-key` + `anthropic-version` | Claude / mimo 等 |
| `openai` | `{base}/v1/chat/completions` | `Authorization: Bearer` | DeepSeek / 通义 / Ollama / vLLM |

系统设置里填 **API Base / API Key / 模型 / 接口协议** 即可切换，不用改代码。

再加新协议（比如 Gemini）：
1. `buildBody()` 加分支
2. `extractText()` 加分支
3. `post()` 加路径与请求头
4. `SettingsService.update()` 的校验里加合法值

## 9. 提示词维护

全部在 `PromptTemplates.java`，按用途分成 6 段，都是「输出合法 JSON」：

| 模板 | 用途 | 关键约束 |
|---|---|---|
| `INTERVIEW_SYSTEM` | 全局铁律 | 真考卷三档、场景化、时效性、只输出 JSON |
| `paperPlanUser` | 出卷计划 | 题量 15-30、每题档位+分值、Σ=100 |
| `questionChunkUser` | 按计划出题 | 按档位出、产出 demands 批改清单、参考答案只覆盖要求 |
| `gradeUser` | 批改 | 按 demands 逐条核对，只给 0-10 表现分；扩展不计分 |
| `paperSummaryUser` | 本卷总结 | 输出短，防截断 |
| `memoryUpdateUser` | 记忆合并 | 条数/字数上限、coverage 只增不减 |
| `digestUpdateUser` | 会话摘要 | 固定长度 |
| `stageSummaryUser` | 阶段总结 | 固定格式输入，产出 `reviewScope` |

**改提示词的三个坑**（都有测试锁着，改完跑 `mvn test`）：
1. 格式串里的字面 `%` 必须写成 `%%`（否则 `String.format` 直接崩）
2. 单次输出不能长——模型思考很吃额度，长 JSON 会被截断
3. 字段名前后端要对齐（踩过 `overview` / `overall` 的坑）

## 10. 出题的四条硬约束

改出题行为时**先看这四条**——它们是产品意图，不只是提示词措辞：

| 约束 | 落在哪 | 怎么验 |
|---|---|---|
| **一题只考 1-2 个知识点** | 提示词 + `Mappings.cap(..., 2)` 数据层卡死 | `knowledgePoints.length ≤ 2` |
| **深度循序渐进** | `PromptTemplates.depthHint(paperSeq, level)` | 第 1 卷不许出现源码/底层字眼 |
| **严格在范围内** | `INTERVIEW_SYSTEM` 铁律 | Java 基础里不许出现 Redis/分布式 |
| **≥1/3 变种题** | `paperPlanUser` 覆盖策略 | 卷间知识点有延续（换个说法也算） |

**深度阶梯**：

| 卷序 | 允许的深度 |
|---|---|
| 1 | 识记与辨析——只考「是什么、怎么用、常见区别」，**禁止源码细节** |
| 2 | 理解与边界——可以问「为什么、什么时候会出错、参数怎么选」 |
| 3 | 原理与实现——可以考底层机制、关键流程、源码级实现 |
| 4+ | 综合与调优——复杂场景、性能取舍、架构权衡 |

岗位难度会调档：**初级**封顶在第 2 档（不考冷门源码与算法），**高级**提前一档。

**分值区间**（`Scoring.normalizePoints(raw, tiers)`）：基础 2-4、中档 4-8、大题 15-20，合计恒为 100。
上限是**软的**——题少时夹着上限凑不满 100，就放开上限把分发完，否则均分全错。
测试要用真实题量（20 题）验证，别用 5 题的小样本（那种样本本身就凑不出合理的分值结构）。

> **经验**：模型不会稳定遵守这些约束。凡是能用数据层卡死的（分值区间、知识点条数、记忆条数），
> 一律在后端夹住；提示词只负责「意图传达」，不负责「保证」。

## 11. 测试

`src/test/java` 覆盖最容易悄悄坏的纯逻辑：

| 测试类 | 锁的是什么 |
|---|---|
| `ScoringTest` | 分值归一化恒等于 100、实得分换算 |
| `MemoryRulesTest` | 记忆并集不丢条目、条数/字数上限 |
| `PromptBudgetTest` | 上下文总量永远有顶 |
| `PromptTemplatesTest` | 每个模板都能安全 `formatted` |
| `MappingsTest` | AI 返回畸形字段时不静默变空 |
| `WebFetcherTest` | 网页正文抽取、SPA 空壳要报错 |
| `WebSearchTest` | 搜索线索解析、失败降级 |
| `MistakeServiceTest` | 错题判定矩阵、幂等收录、手动行保留、cap |
| `NoteServiceTest` | 笔记正文长度/空校验、场景白名单 |

新增业务逻辑时，**先把纯逻辑抽出来再写测试**——这比事后补端到端快得多。
